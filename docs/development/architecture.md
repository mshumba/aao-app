# Architecture and catalog

## Navigation and presentation

`src/app/` is an Expo Router root stack whose first screen is the `(tabs)` group: **Home** `/`, **Topics** `/topics`, **Search** `/search` (accepts initial `q` and `category` and filters by topic in place) and **Account** `/account` (the signed-in profile or a guest card, settings, policies and Delete account). `src/tabBar.tsx` draws the floating tab pill; switching tabs doesn't animate. Topic pages `/topics/[categoryId]`, sermons `/sermon/[id]`, `/saved`, the account settings under `/account/*`, About, Privacy, Terms and Sample screens open over the tabs with a Back (or Close) button. There are no download or watch-history controls.

Onboarding and sign-in routes stack over whatever the viewer was doing and close together when an account is ready: `/welcome` and `/onboarding/*` (first run), the sign-up sheet `/join` (an iOS form sheet), and `/auth/email`, `/auth/password`, `/auth/code`, `/auth/reset`, `/auth/new-password` (modals) and `/auth/callback` (where web and OAuth sign-ins return). `/s/[id]` is a shared link: it lets a guest watch that sermon, then opens `/sermon/[id]`. The root layout's provider order is `MotionProvider` → `AccountProvider` → `PlayerProvider` → `ToastProvider`; `IntentRunner` and `FirstRun` sit beside the player host.

Each tab keeps its own state (typed search, filter, scroll) while you switch. Screens opened over the tabs return with Back; recovery actions ("Browse other topics", "Back to sermons", "Continue as guest") use `exitTo` in `src/navigation.ts`, which returns to the existing tab instead of stacking another (`router.dismissTo` on native; on web, close then switch tab, so browser history keeps one entry per place). The root stack is anchored on `(tabs)`, so a link straight to a sermon or topic opens over Home. Unknown category/sermon links have explicit recovery actions. Route params are normalised (`firstParam`), so a repeated parameter can't break a screen. On web, URL parameters seed the screen on arrival; subsequent typing/filter changes aren't synchronised back into the URL.

`src/theme.ts` holds colour, spacing, radius, type-role and press tokens. The colours are the ivory-and-navy palette (user decision, 14 October 2026): an ivory page (`c.bg`), white raised surfaces lifted by a hairline (`c.border`) or a soft shadow, sand for featured cards (`c.feature`), one navy accent for actions, links, selection and focus (`c.accent`, with `c.onAccent` on it) and gold for editorial eyebrows (`c.gold`). The player and anything drawn over video or artwork use `c.media`, `c.onMedia` and `c.onMediaMuted`, so video stays dark on the light app. `src/ui.tsx` provides shared controls (`Tap` press feedback, buttons, headings with real levels, `SermonTitle`, `SermonRow`, state panels). `src/toast.tsx` shows brief, announced confirmations above the tab bar and dock; `src/share.ts` shares a sermon's link. `src/topics.tsx` owns the topic grid, rows, tags, search filter and the sample-topic notice. `src/navigation.ts` drops repeated taps: each control is locked after it navigates, and an app-wide 350ms window stops a double tap on Back from popping two screens. `src/motion.tsx` keeps the system Reduce Motion setting live for the stack (platform push, or fade) and press feedback (scale, or dim). Side-by-side layouts stack when the reading column is narrow at the user's text size. Text containers grow and screens scroll.

## Catalog model

`src/data/sermons.ts` is the single local catalog of verified source metadata only. `src/data/categories.ts` defines stable editorial IDs. Topic assignments live separately in `src/data/edification.ts`, keyed by sermon ID, so a sermon is stored once even when it belongs to several topics:

```ts
H9sRbSUt0YE: {
  primaryCategoryId: 'spiritual-growth',
  additionalCategoryIds: ['faith'],
  tags: ['discipleship', 'maturity'],
  reviewStatus: 'demo',
}
```

A sermon's topic labels (primary first, or the topic being browsed first) appear above each row's title. Category membership includes primary and secondary IDs. Search intersects the optional selected category with all whitespace-separated query terms across source title, channel, gathering, date, topic labels and tags. Current counts are Spiritual Growth 3, Prayer 2, Faith 2 and Christian Living 0. The empty category is intentional.

**Every topic/tag assignment is dummy data requested for the prototype. No sermon theology or message content has been reviewed.** Each screen that shows topic labels displays the notice “Topics are sample labels, not yet checked against each sermon.”, and each row's accessible name says “Sample topics”. Verified titles are never reformatted; `SermonTitle` only draws the “|” separators in the system face so they don't read as a capital I. Do not turn `reviewStatus` into “approved” without a defined editorial review process.

Verified source fields remain separate: exact `title`, uploader `channel` (not a guarantee of the only speaker), source URL, source page, source thumbnail and ministry-listed duration. Dates appear in the source titles. The four provisional sources are [RCN North America](https://www.rcnnorthamerica.com/) and the linked public [YouTube channel](https://www.youtube.com/@ApostleAromeOsayi). Source spellings are preserved. Do not derive theology, Scripture citations or descriptive summaries from a title.

## Accounts, onboarding and the gate

Accounts are Supabase accounts behind an `AuthBackend` interface (`src/auth/`), so screens never import supabase-js; an on-device stand-in implements the same interface for development and tests. `useAccount()` holds the session, profile, saved sermons, watch progress, onboarding state and the remote `guestWatch` setting. `useGate()` decides whether a guest may watch or save; when not, it stores what was tapped and opens the sign-up sheet, and `IntentRunner` carries it out once the account exists. The session is kept in the Keychain/Keystore on phones. Details, storage keys, test values and App Store notes: [accounts](accounts.md).

## Future persistence

Supabase holds accounts, profiles (display name, topics), saved sermons and watch progress, with row level security (`supabase/migrations/`). The sermon catalog is still a local file. The in-memory catalog model can later map to `sermons`, `categories`, a sermon/category join table (including primary status), and tags. Preserve stable category IDs independently of editable display labels; separate provider/video identity from an app-owned sermon ID when adding another provider. Add verified-at/source provenance and editorial review fields through an explicit migration. Only ingest explicitly approved source material.

Keep querying behind `sermonsInCategory` / `searchSermons` or a future repository adapter so screens need not know whether content comes from a file, cache or service. A later ingestion process must validate unique IDs, topic references, source rights and provider availability; the current tests cover the local invariants. Watch progress is kept per account (below); a full watch history is not built.

## Media

There is **one YouTube player for the whole app** (user decision, 30 September 2026). `src/player/PlayerProvider.tsx` owns the loaded sermon and playback state (a slow "session" context and a per-second "playback" context). `src/player/PlayerHost.tsx`, rendered above the navigator in the root layout, draws the single embed either in the sermon screen's Now Playing slot or docked above the tab bar; the embed keeps the same place in the tree in both, so moving never reloads or restarts it. `src/player/layout.ts` gives the slot and the host the same geometry, and the sermon screen tells the host it is ready once its push transition ends. `src/player/NowPlaying.tsx` has the app's transport (play/pause, back 15s, forward 30s, scrubber, speed); `Embed.web.tsx` / `Embed.tsx` send those commands through the official IFrame API (`playVideo`, `pauseVideo`, `seekTo`, `setPlaybackRate`) and report state, time and duration. YouTube's own controls stay visible; nothing covers the provider once it is ready; the video is at least 200×200 full or docked. The tab bar and dock bar measure themselves (`useChrome` in `layout.ts`), so the dock sits correctly at any text size. On a window too short for a docked video to leave 160px of page (a zoomed-in browser), the dock is a bar only: the video is hidden, paused and kept mounted, and reopening Now Playing resumes it. The scrubber uses react-native-gesture-handler (`GestureHandlerRootView` at the root) so sideways drags scrub and vertical swipes scroll the page.

Playback only starts from the viewer's tap on **Watch sermon** (or **Resume at …**), Play, or a **Continue watching** card (a Watch that needed an account carries on once the account exists). Because the app's Play must be able to start the provider, the native WebView sets `mediaPlaybackRequiresUserAction={false}`; no code path plays without a tap. Leaving the app (background, not iOS "inactive") pauses the sermon (no background audio), and a pause while the player is still loading cancels the queued start. Closing the dock removes the player. Errors that retrying can't fix (removed, embedding disabled, unidentified player) offer Watch on YouTube instead of Try again. No extraction, download or watch-history log exists; only the last position in each sermon is kept (below). YouTube is provisional; Vimeo/Bunny remain possible later decisions, and would be needed for lock-screen or background audio.

Playback is gated for guests (see [accounts](accounts.md#the-guest-gate)): Watch asks for an account unless the sermon came from a shared link or the remote setting opens it. Third-party thumbnail/player traffic is described in the privacy screen.

### Watch progress

For a signed-in viewer, `PlayerProvider` keeps their place in each sermon through `useAccount().saveProgress` (stored in Supabase's `watch_progress`, see [accounts](accounts.md#where-data-is-kept)). It saves every 15 seconds while playing, on pause, when the player docks or closes, when another sermon loads and when the app goes to the background. A save is skipped when nothing changed, and for a sermon less than 15 seconds in that was never saved. Saves apply in memory at once and are written one at a time in the background, latest position per sermon only, so they never wait on the network or hold up playback. Within the last 30 seconds (or the last 2% of a long sermon) a sermon counts as finished. The rules live in `src/player/progress.ts`.

`load()` starts a sermon from the saved place through the IFrame API's `start` parameter, and the Now Playing panel says **Resuming at 42:10 · Start over** until the viewer starts over (a seek to 0) or is two minutes past it. Before Watch, the poster reads **Resume at 42:10** with a progress bar along its bottom edge. Home's **Continue watching** row (`src/continueWatching.tsx`) lists up to six unfinished sermons, most recent first, above Featured; it's hidden for guests and when there's nothing to continue. A card opens the sermon and resumes it in one tap: it leaves a short-lived request (`requestWatch` in `src/navigation.ts`) that the sermon screen carries out once it is staged, so the player never appears in the dock first. Finished sermons start from the beginning again.

## Native project

The native projects are generated (`ios/`, `android/` are git-ignored). `plugins/with-ios-scene-lifecycle.js` switches the generated iOS app to Expo's `ExpoAppSceneDelegate`, because iOS 27 won't launch an app built with its SDK without the scene life cycle; remove it once Expo's template adopts scenes. The home-screen name is "AAO" and the App Store Connect name "AAO App"; the iOS bundle identifier and Android package are `com.mshumba.aao` (user decision, 14 October 2026; permanent once the App Store Connect record exists). `userInterfaceStyle` is `light`, and the window and splash background are the ivory `#f7f4ee`. `app.config.ts` wraps `app.json` only to leave out the Sign in with Apple entitlement for free Personal Team builds (`AAO_PERSONAL_TEAM=1`). `expo-updates` is configured with the `appVersion` runtime policy ([releasing](releasing.md#over-the-air-updates-eas-update)). The icon, adaptive icon, splash mark and favicon in `assets/` are drawn by `assets/icon-source/render.mjs` (`npm run icons`): a serif "AO" (Newsreader SemiBold, italic O) in ivory on the navy accent for the app icon, adaptive icon (on a navy `adaptiveIcon.backgroundColor`) and favicon, and in navy on the ivory splash. The colours there must change with `src/theme.ts` and `app.json`. The mark is a starting point rather than a brand decision.

## Headlines and player states (30 September 2026, user decision)

`src/data/display.ts` holds short editorial headlines and event lines, shortened from the verified titles. Rows, Home, Now Playing and the dock lead with them; the exact title stays in `sermons.ts`, is shown under "On YouTube" on the sermon screen and is still searched. The Now Playing controls are back 15 / play-pause / forward 30 with speed between the times. The status line is always announced but shown only when it asks something of the viewer: loading, press play, still loading, tap play in the video (a browser refused the app's start), or ended. A failure is shown where the video was, with only the actions that can work, and takes keyboard focus when it removed the focused control. Only a playing video is pinned; a poster or error scrolls with the page.
