# Contributing

Keep changes focused on the sermon experience. Preserve exact source titles, legal provider controls and the explicit sample status of topic data. A working menu item must lead to a built screen with a sensible back path.

## Accounts and copy

- **Gate actions, not screens.** Guests can open every screen. An action that needs an account goes through `useGate().require(intent)`, so the sign-up sheet opens and the action carries on afterwards. Don't add a sign-in wall to a route. [Accounts](accounts.md) explains the gate and the remote `guest_watch` setting.
- **Screens use `useAccount()`, never supabase-js.** Service details stay in `src/auth/`, behind `AuthBackend`. Schema changes go in a new file in `supabase/migrations/`.
- **Honest copy.** The app isn't official or endorsed by the ministry; never imply it is. Accounts are "free", not "free forever". Normal UI has no demo or test language; the stand-in's test-mode notice only shows when `mode === "local"`.
- **Never log or store credentials.** No `console.log` of passwords, codes, tokens or auth responses. Passwords and codes go only to the account service; the session lives only in Supabase's storage adapter (the Keychain on phones). No secret or `service_role` key in the app, `.env`, `eas.json` or tests.
- **Tests use the local service.** Playwright runs with `EXPO_PUBLIC_AUTH_MODE=local`; never point tests at a real Supabase project or a real inbox. Use `example.com` addresses and the [test values](accounts.md#local-test-values).

## Development loop

1. Start from the locked dependencies with `npm ci` and use the documented Node version.
2. Make a focused change using shared controls/tokens. Keep text flexible, touch areas at least 48 logical units, and topic scope visible and removable.
3. Run typecheck, lint, Doctor, all-platform export and relevant tests. The required CI performs the same checks with frozen dependencies and bundled Chromium.
4. Inspect small-phone and wide layouts. Check empty/invalid data, reduced motion and back/dismiss behavior. For player changes, run the optional live browser probe and the native device checklist.
5. Describe the behavior change, evidence and remaining limits. Do not describe compilation or a browser viewport as a native-device pass.

`tests/catalog.spec.ts` checks the bundled sample's exact verified titles, that records carry no topic fields, that the sample matches what the import writes, category membership, search, event lines and series order. `tests/parseTitle.spec.ts` covers the title parser on one real title per house style. `tests/catalogue.spec.ts` drives the library's sync with a fake Supabase and storage: first launch online and offline (the bundled sample), a saved copy and its "changed since" sync, the weekly full sync, damaged copies and failing storage. `tests/topics.spec.ts` exercises the tabs and the state each keeps, topic cards and pages with their return path, old Topics links landing on Search, empty and unknown topic recovery, 320px overflow and small targets. `tests/core.spec.ts` covers guest flows, heading levels, the player through a deterministic fake IFrame API (`tests/fixtures.ts`: Watch auto-start, transport commands, docking that keeps the same player across tabs, replacing the docked sermon, pausing when the app is hidden, errors that only offer retry where it can help), double-tap guards on rows, Watch and Back, repeated link parameters, missing artwork, sample screens without console errors, and press feedback under Reduce Motion; `tests/onboarding.spec.ts` covers the first launch (welcome once, topics, account, name, done, and leaving as a guest). `tests/gate.spec.ts` covers guest browsing, Watch and Save asking for an account and then carrying on, closing the sheet, shared links and code errors. `tests/account.spec.ts` covers the signed-in profile, sign-out, saving, deletion, and password sign-in, sign-up and reset. `tests/auth-edge.spec.ts` runs sign-out and link exchange (`src/auth/supabaseSession.ts`) in Node against the real supabase-js with a stand-in server; `tests/android-google.spec.ts` drives the choice between Google's own sheet and the web flow on Android, iPhone, Expo Go and the web without a device; `tests/saved-order.spec.ts` covers the save queue (`src/auth/savedWrites.ts`); `tests/account-switch.spec.ts` switches accounts while the first account's progress is still loading. `tests/offline-launch.spec.ts` opens the app on a weak connection in Node against the real supabase-js (the launch cap, renewals, account data sent only with the account's own session, deadlines, offline deletion and sign-out). `tests/watch-queue.spec.ts` covers the watch-position queue (`src/auth/watchQueue.ts`): retries and backoff, order, places saved later on another device, changing account and refusals; `tests/offline-progress.spec.ts` covers Continue watching and saving places offline in the app. `tests/failure-reports.spec.ts` covers what failure reports send to Sentry and how often (`src/lib/failureReports.ts`). `tests/apple-tokens.spec.ts` runs Sign in with Apple token revocation in Node with stand-ins for Apple, the database and the Edge Function: the client secret's claims and signature, Apple's request bodies and errors, the order of storing, revoking and deleting, and retries. Browser fixtures abort thumbnail requests so required checks remain independent of remote image availability. Live playback is deliberately an opt-in network check, not a CI availability dependency.

`tests/reminders-plan.spec.ts` covers what the daily path reminder schedules, in Node: the day due, the time and missed days. `tests/reminders.spec.ts` covers the opt-in in the app with a stand-in phone (the offer, the time sheet, Not now, a phone that says no, Account, signing out and deleting the account, a tapped reminder) and that the web offers nothing.

Run `npm audit` when changing packages and assess direct impact/compatible updates. The initial toolchain audit reported moderate transitive findings and no high/critical findings; its suggested blanket fix required incompatible downgrades. Do not use `npm audit fix --force` as an automatic remedy. Recheck before an actual release.

## Public-source hygiene

Local historical plans, private context, agent instructions, design references, generated screenshots/logs and machine-specific evidence are preserved but ignored. Never use `git add -f` to sweep them into a public repository. `.gitignore` is a guardrail, not proof that staged files are safe. Inspect `git status`, the staged file list and each diff; search for credentials, local paths, account identifiers and private text before publication.

Intended source allowlist: `src/`, `tests/`, `scripts/`, `assets/`, `plugins/`, `supabase/`, `docs/development/`, `.github/workflows/ci.yml`, README, lock/package files, `app.json`, `app.config.ts`, `eas.json`, TypeScript/ESLint/Playwright config, `.env.example` and `.nvmrc`/`.gitignore`. Review scripts individually; do not stage generated evidence. Only synthetic values belong in examples and tests. `.env` stays untracked; EAS holds build-time values.
